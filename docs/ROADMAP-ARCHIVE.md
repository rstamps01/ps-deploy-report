## Done — Log-formatting hygiene (v1.5.5, 2026-03-21)

*Source: Operator-visible defects in the Reporter-tile run captured in `import/Assets-2026-04-21c/output-results-logs-2026-04-21.txt`. Both items shipped in v1.5.5 — see CHANGELOG `[1.5.5]` for detail.*

| ID     | Item | Priority | Status | Notes |
|--------|------|----------|--------|-------|
| RM-14a | **`SensitiveDataFilter` narrowed to real credential shapes.** The previous substring scanner redacted ANY message containing the literal word "password"/"token"/"key"/etc., mangling narrative operator prose ("Primary switch password failed authentication — retrying with fallback candidate 2/3" → "Primary switch PASSWORD_[REDACTED]— retrying...") and even consuming the RM-1 redaction sentinel `<switch-password>` inside our own display-command strings. The filter now compiles a single `_CREDENTIAL_RE` regex that requires a `:` or `=` separator between a recognised key and a concrete value, with an allowlisted filler-verb clause (`is`/`was`/`received`/`provided`/...) for prose disclosures and an optional prefix-word clause so `Authorization: Bearer <token>` still fully redacts. The legacy `<KEY>_[REDACTED]` marker format is preserved so downstream consumers that search for it keep working. | Low (UX + security clarity) | Done | `src/utils/logger.py` (`SensitiveDataFilter._CREDENTIAL_RE`, `_CREDENTIAL_FILLER_VERB`, `filter`, `_redact_match`); tests: `tests/test_logging.py::TestSensitiveDataFilterRM14` (5 new: narrative prose preserved, RM-1 sentinel preserved, common English preserved, key/value and prose-disclosure still redacted, `Authorization: Bearer` token redacted). |
| RM-14b | **`execute_remote` post-command transcript classified as `info`.** The `echo $?` / return-code / `[Command completed in Xs]` tail that `ScriptRunner.execute_remote()` appends is shell transcript framing, not diagnostics. Previously, when `rc != 0` the first two lines were emitted at `error` level, producing misleading log blocks like `[ERROR] vastdata@host:~$ echo $?` / `[ERROR] 1` / `[INFO] [Command completed in 32.93s]` — every non-zero command gave operators two spurious red lines to chase even though the RM-8 stderr classifier already flagged the real diagnostic above them. Both lines now emit at `info` so operator scans for `[ERROR]` surface only genuine diagnostics. | Low (UX) | Done | `src/script_runner.py::ScriptRunner.execute_remote` (post-command emit levels); tests: `tests/test_script_runner.py::TestExecuteRemotePostCommandLevel` (2 new: failure and success cases both assert `info` level on the prompt + rc lines). |
| RM-14c | **Tool-emitted `{WARNING}` / `{CRITICAL}` tags on stdout promote to `[WARN]` instead of `[INFO]`.** `ScriptRunner._classify_output_line()` had a single narrow `{ERROR} general exception` branch; every other `{<LEVEL>}` tag from a remote VAST tool fell through to `info`. *Source: live Tech-Port mode validation against `selab-var-202` (Eth) and the mammoth IB cluster (live access lost 2026-05-15). Stack: TP-1 → TP-2 → SR-1 → SR-5 → `--from-json` → SR-3 → SR-4.
